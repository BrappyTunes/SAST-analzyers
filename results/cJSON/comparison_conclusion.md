# SAST vs LLM Comparison Conclusion

## Executive summary
SAST tools flagged 103/902 functions (11.4%) as vulnerable; LLM flagged 69/902 (7.6%). Agreement on vulnerability is low: only 33 functions were flagged by both, representing 32% of SAST positives and 48% of LLM positives. Binary agreement rate is 88.25%, but this is inflated by the large number of clean functions (763). The tools disagree on 106 functions (70 SAST-only, 36 LLM-only). CWE overlap on jointly flagged functions is minimal (3/33, 9.1%), indicating poor semantic alignment. SAST produces many low-severity, generic findings (CWE-398: 63) and false positives in test code; LLM findings are more concentrated on memory safety (CWE-125, 476, 787) but include 36 unique findings that SAST missed. Overall, neither tool is sufficient alone; combined use is recommended.

## Agreement assessment
The binary agreement rate of 0.8825 is misleading because 763/902 (84.6%) functions are clean by both. The real signal is in the disagreement: 70 SAST-only vs 36 LLM-only. SAST-only findings are dominated by CWE-398 (indicator of poor code quality) and CWE-476 (null pointer dereference) in test files (e.g., tests/unity/test/tests/testunity.c, tests/parse_array.c). Many SAST-only findings are likely false positives or low-risk issues in test code. LLM-only findings (e.g., CWE-125 in UnityPrint, CWE-476 in suffix_object) are in production code (cJSON.c, unity.c) and represent potential real memory safety issues that SAST missed. The low CWE overlap (3/33) on jointly flagged functions suggests that even when both agree a function is vulnerable, they often identify different vulnerability types, indicating complementary detection capabilities.

## SAST strengths
SAST flags more functions overall (103 vs 69) and has broader coverage of CWE types (12 distinct CWEs vs 17 for LLM, but SAST has more findings per CWE). SAST is particularly strong at detecting null pointer dereferences (CWE-476: 21) and buffer overflows (CWE-126: 17, CWE-119: 14, CWE-120: 10). It also catches code quality issues (CWE-398: 63) that LLM ignores. SAST is deterministic and reproducible, making it suitable for CI/CD integration.

## LLM strengths
LLM findings are more focused on memory safety: CWE-476 (18), CWE-125 (11), CWE-787 (9), CWE-416 (5), CWE-190 (4). These are high-severity issues. LLM identifies 36 functions that SAST misses, including critical ones like UnityPrint (CWE-125) and suffix_object (CWE-476) in production code. LLM has a lower false positive rate in test code: only 3 of 36 LLM-only findings are in test files (testNotEqualMemoryEachEqualExpectedNull, cjson_set_bool_value_must_not_break_objects, and one other), whereas SAST-only findings are heavily concentrated in test files (e.g., 10+ in testunity.c alone). LLM also provides more specific CWE classifications (e.g., CWE-125 vs CWE-119) which aids remediation.

## Key risks
1) SAST-only findings in production code (e.g., cjson_minify_should_remove_single_line_comments with CWE-120/CWE-476) may be false positives but need manual review. 2) LLM-only findings in production code (e.g., UnityPrint, skip_multiline_comment, suffix_object) are high-risk because they are memory safety issues that SAST missed. 3) The 33 functions flagged by both have only 3 matching CWEs, meaning even when both agree, they often disagree on the vulnerability type, which could lead to incomplete fixes. 4) SAST's heavy reliance on CWE-398 (63 findings) is a noise source that may desensitize developers to real issues.

## Recommendations
1) Use both tools in tandem: SAST for broad coverage and LLM for deep memory safety analysis. 2) Prioritize LLM-only findings in production code (cJSON.c, unity.c) for immediate manual review. 3) Triage SAST-only findings in test code as low priority unless they involve memory safety CWEs (CWE-120, 126, 119). 4) For the 33 jointly flagged functions, manually inspect both CWE sets to ensure all vulnerability types are addressed. 5) Consider suppressing CWE-398 in SAST to reduce noise. 6) Validate LLM findings with a second LLM pass or runtime testing (e.g., fuzzing) to confirm false positives.
